# note-make：把对话整理成笔记

把当前对话中值得保留的内容整理成一篇结构清晰的私人 Markdown 笔记，格式按 self-hosted Discourse 的兼容子集检查。默认保存到当前项目的 `.notes/`。

Discourse 参考只约束格式，不改变“笔记是写给用户自己看”的假设；不要为了让外部读者读懂而额外解释或调整语气。

## 执行顺序

1. 确定记录范围和笔记类型；不确定时只问一个关键问题。
2. 确定目标路径，并在目标目录中查找同主题笔记（见第五节）。
3. 读取 `references/discourse-markdown.md` 和对应类型的参考文件（混合型可读两份）。
4. 按参考文件的结构写作，同时遵守下面的通用风格，并在写入时执行脱敏。
5. 写入或修改文件；如果文件包含 `$`，运行本 skill 目录下的 `scripts/fix-mathjax.py <path>`。
6. 按清单自检，回复路径、一句话摘要和脱敏情况。

这个技能以整理已有对话为主，只在关键信息缺失或结论不确定时提问。

## 一、先判断三件事

### 1. 记什么

- 用户明确指定范围时（如“只整理安装部分”“整理刚才讨论的缓存策略”），以指定范围为准。
- 没有指定时，整理本次对话中已经形成结论、步骤或知识链的部分。
- 不要为了凑篇幅写入寒暄、试错过程、被否决的方案；只有当它们能解释“为什么最终这样做”时才保留。
- 对话很长且主题分散时，先问一句“这次想整理哪一部分？”，只问一次。
- 缺少关键信息时问一句；不要编造事实、版本号、命令输出或链接。

### 2. 笔记类型

- **操作总结型**：对话主要在讲“怎么做”——命令、配置、安装、排错、流程。
- **信息调研型**：对话主要在讲“是什么 / 怎么样 / 选哪个”——事实、对比、结论、适用条件。
- **知识学习型**：对话主要在讲“为什么 / 原理 / 概念”——定义、机制、理论、学习。
- **混合型**：以最终目的为主类型搭骨架，另一类作为其中一节。例如“先学概念再动手”的笔记，整体按学习型组织，把操作放进“应用”一节。
- 不确定时，按用户最后想要的结果判断：想要能照着做的步骤 → 操作型；想要一个判断或答案 → 调研型；想要理解一个东西 → 学习型。仍然不确定就问一句，例如：“这篇笔记你更想要能照着做的步骤、一个判断或结论，还是概念梳理？”

### 3. 写到哪

路径优先级从高到低：

1. 用户在调用参数或对话中明确指定的文件 / 目录。
2. `NOTE_MAKE_DIR` 环境变量（用 `printenv NOTE_MAKE_DIR` 读取；空值视为未设置）。
3. 当前项目根目录下的 `.notes/`。

项目根目录的确定方式：在 git 仓库内用 `git rev-parse --show-toplevel`；不在 git 仓库时用当前工作目录。

路径判定：

- 已存在且是目录，或以 `/` 结尾 → 目录，在目录中生成文件名。
- 以 `.md` 结尾 → 直接使用该文件。
- 无扩展名且路径不存在 → 问一次“这是文件名还是目录？”，不要自行猜测。
- 用户给的是相对路径 → 相对项目根目录解析。
- 目录不存在时 `mkdir -p`；路径存在但没有写权限时，请用户换一个可写路径，不要自动换路径。

## 二、交互边界

- 操作型：信息足够就直接写；缺少关键前提（操作系统、版本、权限）时问一句。
- 调研型：结论不确定时先与用户确认；确认不了就不写进笔记，不要用模糊措辞伪装成定论。
- 学习型：默认不测验。只有用户明确要求（`/note-make quiz`，或在整理笔记的请求里说“考考我 / 测一下我 / quiz me”）才启用；题目 1–10 道，按主题复杂度决定，不要为凑数出题。
- 用户已经说“直接写 / 不用问”时，跳过所有澄清，按现有信息整理；不确定的结论不要伪装成定论。
- 澄清问题最多 1–2 个真正影响成稿的问题；用户主动要求的测验、同主题修改的重写 / 覆盖 / 类型确认不计入。不要为了走流程而提问。

## 三、通用写作风格（所有类型）

### 以对话校准知识基础

- 从用户用过的术语、问过的问题、做过的纠正判断其掌握程度。
- 用户能自然使用的概念，不再解释；用户明确问过的基础点，才用一两句话补齐。
- 不要因为用户问了一个问题就假定其不懂整个领域，也不要因为用户没问就假定其全懂。
- 解释深度以“能读懂本篇”为准，不写教科书式的背景铺垫。

### 避免居高临下的表述

- 除非对话里确实出现了误解，否则不要使用“不是……而是……”“很多人以为……其实……”“你可能不知道……”这类预设用户无知的句式。
- 需要澄清时，直接给正确表述和适用边界，例如“这里的 X 指……；Y 是另一回事”，而不是先虚构一个错误理解再纠正。
- 语气平实。不写“非常重要”“一定要记住”之类的大段强调；重点靠结构和位置体现，不靠加粗堆叠。

### 结构要有逻辑

- 先定一条主线，再排章节。常见主线：
  - 操作型：前提 → 核心步骤 → 验证；易错点融入对应步骤。
  - 调研型：结论 → 关键信息 → 依据 / 背景。
  - 学习型：概念 → 机制 → 应用 / 例子 → 待深入；适用边界和常见误区融入相关段落。
- 章节之间要有递进或分层：后一节应建立在前一节之上，或回答前一节留下的问题。不要把互不相关的点摊平成清单。
- 同层级用同一粒度；需要展开时用 `###` 下沉，不要在一节里混入多个层级的内容。
- 如果某个具体问题能自然推广到更一般的情况，且不会显著增加篇幅，可以用一小段或一句“更一般地说……”点出来；否则保持具体，不要为了抽象而抽象。
- 列表用于并列项或步骤，不要把所有内容都塞进列表。段落短，一段只讲一件事。

### 内容取舍

- 先写结论或目的，再写支撑；不要用大段背景铺垫开头。
- 对结论没有影响的信息删掉或压缩成一句。
- 保留用户自己的术语和叫法；需要统一时，在首次出现处说明“下文统一称 X”。
- 笔记要能脱离对话独立阅读。不要写“刚才说的”“上面的方案”这类依赖上下文的指代；必要时应复述关键背景。
- 写作语言跟随对话的主语言。技术术语保留原文；需要中文对照时，在首次出现处用括号补充，不要通篇翻译。
- 不编造对话中没有的事实。

### 脱敏（所有类型）

- 只脱敏凭据类信息：密码、API key / token、Cookie、私钥，以及连接串中的用户名和密码。连接串保留 scheme、主机、端口和库名，只替换凭据段。
- 代码块中保留变量名和命令结构，只替换值，例如 `OPENAI_API_KEY=<redacted>`；散文中的替换值用行内代码包住。
- 已经是占位符或占位值的（如 `<password>`、`<token>`、`<redacted>`）保持不变，不要二次替换。
- 内网 IP / 主机名、邮箱、手机号、本地绝对路径默认保留。用户明确要求去除或脱敏其他内容时，以用户说明为准。
- 笔记正文不写“已脱敏”之类的说明；在最终回复里告知用户脱敏了几处，必要时列出变量名，不列出值。
- 更新已有笔记时，只处理本次新增或修改的内容，不回扫旧内容。
- 首次写入 `.notes/` 且该目录未被 git 忽略时，提醒一次；不要自动修改 `.gitignore`。

### Discourse 格式兼容

写任何笔记前，读 `references/discourse-markdown.md`。这里的规则只约束格式，不改变“笔记默认是私人笔记、读者是用户自己”的写作假设；不要为了论坛读者额外解释或调整语气。核心规则：

- 使用 CommonMark/GFM 的稳定子集：标题、段落、列表、引用、围栏代码块、表格、链接、行内代码、粗体 / 斜体。
- 只用围栏代码块（三个反引号），标注语言；不要用缩进代码块。
- 一个文件只用一个 `#` 标题；章节用 `##`，子节用 `###`，不要跳级。
- 不使用 YAML frontmatter、原始 HTML、`<details>`、脚注 `[^1]`、GitHub 警告块 `[!NOTE]`、任务列表 `- [ ]`、`==高亮==`、wiki 链接 `[[...]]`、目录宏。
- 表格只用于真正的对比或矩阵，不要合并单元格。
- 链接用完整 URL 或行内链接；不要用相对路径链接到本地文件。图片需要先上传到 Discourse，正文里不要放本地图片路径。
- 数学公式仅在目标论坛启用 MathJax 时使用。行内公式写成 ` $...$ `，前后各留一个半角空格（紧贴中文或标点时也要留；行首/行尾可省略）。`$$...$$` 独占一行，前后空行。代码块和行内代码里的 `$` 不参与公式。Mermaid 仅在启用对应插件时使用；否则用文字或代码表达。
- 正文中避免 `#标签` 形式，需要时放进行内代码。

## 四、三种笔记类型

根据类型读取对应的参考文件，只读需要的文件（混合型可读两份）：

- 操作总结型 → `references/command-note.md`
- 信息调研型 → `references/research-note.md`
- 知识学习型 → `references/learning-note.md`

### 操作总结型（摘要）

- 精简优先。能一行命令说清，就不写一段话。
- 需要时在开头写“前置条件”：操作系统、运行时、版本硬限制、权限、依赖。只写会影响成败的条件。
- 每节先用短标题概括操作，再给可直接复制运行的 shell code block；block 后只在易错处补一句说明。
- 命令用实际验证过的版本，包含必要的 `sudo`、工作目录、环境变量；占位符用 `<...>` 并在首次出现处说明。
- 给出验证命令或预期结果。易错点和排错说明融入对应步骤，不单设“常见问题”章节。
- 不解释命令的原理；需要时链接到另一篇笔记或一句话带过。

### 信息调研型（摘要）

- 开头先给结论或关键信息，不要埋在后面。
- 不确定的结论先与用户确认；确认不了就不写进笔记，不要伪装成定论。
- 未决问题不写进笔记，也不单设“未决问题”章节。
- 避免大段加粗或强调。非关键信息压缩或删除，对结论没有影响的直接不写。
- 区分“已确认的事实”和“推断”，但不要给每句话都加置信度标签。
- 推荐一个选项时，说明它在什么条件下成立，以及什么情况下应该改选。

### 知识学习型（摘要）

- 从基本概念和定义出发，但只写理解本篇所需的定义；用户已经掌握的不要展开。
- 默认不测验。只有用户明确要求（`/note-make quiz`，或在整理笔记的请求里说“考考我 / 测一下我 / quiz me”）才启用；题目 1–10 道，按主题复杂度决定，不要考偏题或冷知识。
- 测验中发现缺失或错误：当场温和提醒；写笔记时在对应概念或机制处自然融入正确理解，不单设“概念校准”章节，也不写“你错了”。
- 用户跳过测验：默认其大致掌握基础，笔记中不再铺陈入门定义，直接进入关键知识；仍可用一句话给出工作定义作为锚点。
- 对话信息太少、无法判断要整理哪部分知识时，问一句“这次想整理哪部分？”，并默认跳过基础知识。
- 组织方式：概念 → 机制 / 原理 → 例子 / 应用 → 待深入。适用边界、失效条件和常见误区融入相关段落，不单独设“边界与常见误区”章节。层层递进，不要把知识点摊平成清单。

## 五、文件命名与写入

### 文件名

- 默认：`YYYY-MM-DD-<slug>.md`，日期用 `date +%F` 获取，不要凭记忆。
- slug 用简短、可读的 kebab-case；优先英文；没有合适英文时用中文短语，去掉标点和空格。控制在 50 字符以内。
- 标题要具体，能说明这篇笔记解决什么问题；不要用“对话笔记”“总结”这类空标题。
- 同一主题重复整理时，直接修改原文件，不生成 `-2`、`-3`。

### 同主题笔记

- 写入前先在目标目录（含子目录）查找 `.md` 文件：slug 相同、标题相同，或章节结构高度重合，满足其一即视为同主题。
- 多个候选时问一次“更新哪一份？”，不要自动挑最近修改的。
- 默认只做针对性修改，保留无关内容；不要整篇重写。
- 新信息会影响超过一半的章节，或需要调整章节顺序 / 结构时，问一次“针对性修改还是整篇重写？”
- 新信息与旧内容冲突时，问一次“以新信息覆盖旧结论吗？”
- 已有笔记类型与本次不同，或目标文件不是 note-make 生成的结构时，先问一次，不直接改。
- 用户明确指定了一个已存在的 `.md` 文件时，视为要求更新该文件；先读取，再按上面的修改边界处理。
- 保持原文件名和创建日期；不增加“更新”章节。

### 写入前后

- 写入前在内部确定标题、类型和目标路径；只有路径冲突、需要覆盖、或类型拿不准时才问用户。不需要向用户展示完整草稿，除非用户要求。
- 写入或修改后，如果文件包含 `$`，运行本 skill 目录下的 `scripts/fix-mathjax.py <path>`；`python3` 不可用时跳过，按写作规则手工检查。也可以对已有笔记手动运行该脚本（`--dry-run` 只报告不写入）；脚本只处理含 LaTeX 命令的行内公式。
- 按下方清单自检。
- 只回复文件路径、一句话说明整理了什么，以及脱敏情况（脱敏了几处；必要时列出变量名，不列出值）。不要在聊天里重复整篇笔记。
- 如果用户要求发布到 Discourse，提醒：本地图片和相对链接需要先处理；正文的一级标题可能与主题标题重复。

## 六、写入后自检

- 标题具体，开头能看出这篇笔记的结论或目的；章节有主线，后一节承接前一节，不是平铺清单。
- 没有解释用户已经掌握的概念；没有“不是……而是……”式的预设无知。
- 操作型：命令可直接复制；前置条件和易错点齐全，易错点已融入对应步骤；没有把输出混进命令块。
- 调研型：结论在前；未决问题没有写进笔记；非关键信息已删减。
- 学习型：基础概念的处理符合用户情况；测验发现的缺口已在对应概念 / 机制处自然融入，没有单独的“概念校准”或“边界与常见误区”章节。
- 凭据类信息已脱敏；内网地址、邮箱、手机号、本地路径按约定保留。
- 没有 YAML frontmatter、原始 HTML、脚注、任务列表等 Discourse 不兼容写法；行内公式前后有空格。
- 没有模板占位符、空章节、编造的事实；文件路径和文件名符合规则。
