# 信息调研型笔记

## 适用场景

对话主要在回答“是什么 / 怎么样 / 选哪个 / 是否值得”。读者想要一个结论或判断，而不是操作步骤。

## 结构

按以下顺序组织；没有内容的小节直接省略。

1. `# <结论式或问题式标题>`：结论已经明确时用结论式，例如“本地优先的同步方案更适合离线场景”；用问题式标题时，开头必须给出当前答案，例如“X 和 Y 应该选哪个？”之后直接说明默认选哪个。
2. 开头一段：直接给结论或当前答案。不要先铺垫背景。
3. `## 关键信息`：支撑结论的 3–6 条要点。每条尽量带一个事实、数字或条件。
4. `## 依据`：只保留支撑结论的事实、数据和来源。用行内链接；来自本次对话的信息注明“来自本次对话”。
5. `## 建议`：可选。如果用户需要做选择，给出推荐选项、适用条件，以及什么情况下改选。

未决问题不写进笔记，也不单设“未决问题”章节。

## 写作规则

- 结论前置。不要把最重要的判断埋在最后。
- 如果结论依赖条件，先列出决定条件，再按条件给结论；不要用一句“看情况”结束。
- 不确定的结论先与用户确认；确认不了就不写进笔记，不要用模糊措辞伪装成定论。
- 区分“已确认的事实”和“推断”，但不要给每句话都加标签。通常只在关键处标注。
- 避免大段加粗或强调。重点靠位置和句子结构体现，不靠连续加粗。
- 非关键信息压缩或删除；对结论没有影响的直接不写。
- 不做无意义的背景介绍。读者需要的是判断依据，不是百科条目。
- 推荐一个选项时，说明它在什么条件下成立；如果条件变化会改选，也写出来。
- 来源用行内链接。不要用脚注，Discourse 兼容性不稳定。
- 如果对话中出现了多个候选方案，用一张小表对比决策相关的列；不要把所有属性都塞进表格。
- 不要写“综上所述”“总而言之”这类收尾套话。

## 示例

````markdown
# 小团队文档同步：本地优先方案更适合离线场景

如果团队经常在弱网或离线环境工作，优先选本地优先、可离线编辑的同步方案；如果所有人都在稳定网络下协作，托管式方案更省维护成本。

## 关键信息

- 本地优先方案把完整数据保存在每台设备上，断网时仍可读写，恢复网络后合并变更。
- 托管式方案依赖持续连接，离线体验取决于客户端缓存能力。
- 本地优先方案的冲突处理更复杂，需要明确“谁最后写入”或使用 CRDT 一类的合并策略。
- 团队规模小于 10 人时，维护成本通常不是主要瓶颈；跨地域、跨时区协作时，冲突处理会成为主要成本。

## 依据

- 本次对话中确认的使用场景：经常出差、会议室网络不稳定、需要离线改文档。
- 关于 CRDT 与最后写入策略的差异，可参考 [CRDT 入门](https://crdt.tech/)。

## 建议

默认选本地优先方案；如果团队没有离线需求，且更看重零维护，则改选托管式方案。
````
