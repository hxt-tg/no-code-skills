# 知识学习型笔记

## 适用场景

对话主要在讲概念、原理、机制、理论。读者想要理解一个东西，而不只是得到一个答案或一组步骤。

## 结构

按以下顺序组织；根据主题和对话内容取舍。

1. `# <概念或主题>`：标题用读者要理解的对象，不用“学习笔记”这种空标题。
2. 开头一段：说明这篇笔记要解决的问题、核心结论，或读者读完后能理解什么。
3. `## 概念`：给出工作定义。只写理解本篇所需的定义；用户已经掌握的概念不要展开。
4. `## 机制 / 原理`：分层解释“它如何工作”。从核心机制开始，再进入细节；每一层回答上一层留下的问题。
5. `## 例子 / 应用`：优先用对话中出现过的例子；没有时构造一个最小示例，并标明“示例”。
6. `## 待深入`：可选。列出本次没有展开、但值得继续查的问题。

适用边界、失效条件、常见误区和测验发现的缺口，不单独设章节；按认知逻辑融入 `概念`、`机制 / 原理` 或 `例子 / 应用` 的对应位置。

## 写作规则

### 测验与基础

- 默认不测验。只有用户明确要求（`/note-make quiz`，或在整理笔记的请求里说“考考我 / 测一下我 / quiz me”）才启用。
- 启用后，题目 1–10 道，按主题复杂度决定，围绕理解本篇所需的前置概念；不要考偏题、冷知识或记忆题。
- 一次问一题或一小串，等用户回答后再继续。用户答错或答不全时，先温和指出，再给出正确理解；不要连续追问，不要让用户感到被审问。
- 测验发现缺失或错误：当场温和提醒；写笔记时在对应概念或机制处自然融入正确理解，不单设“概念校准”章节，也不写“你错了”。
- 用户跳过测验：默认其大致掌握基础，不再追问。笔记中不要铺陈入门定义，直接进入关键知识；可以用一句话给出工作定义作为锚点。
- 对话信息太少、无法判断要整理哪部分知识时，问一句“这次想整理哪部分？”，并默认跳过基础知识。

### 组织知识

- 从基本概念和定义出发，但只写理解本篇所需的定义。不要为了完整性写教科书章节。
- 层层递进：概念 → 机制 → 例子。每一节应建立在前一节之上，或回答前一节留下的问题。
- 适用边界、失效条件和常见误区融入相关段落，不单独设“边界与常见误区”章节。例如讲完机制后补一句代价或限制，或在例子后说明它成立的前提。
- 用对话中用户自己的说法和例子；需要引入新术语时，在首次出现处用一句话定义。
- 例子优先于抽象描述。一个最小例子通常比三段定义更有用。
- 区分“定义”“机制”“实现细节”“类比”。类比可以帮助理解，但要标明它只是类比，并说明它在哪里失效。
- 不追求知识点的数量。与本次目标无关的内容放进“待深入”或直接省略。
- 如果用户的目标是实践，最后一节把概念连回实际决策；如果目标是理论，保持机制部分为核心。

## 示例

````markdown
# 数据库索引为什么能加速查询

索引的核心作用是把“逐行扫描”变成“按顺序定位”，代价是额外的存储空间和写入维护成本。

## 概念

索引是数据库为某一列或几列维护的辅助数据结构，保存排好序的键与对应行的位置。查询时，数据库可以先在索引中定位，再回到表中取数据。

## 机制 / 原理

以 B-tree 索引为例：

1. 索引按键值有序组织成多层节点，根节点指向若干子节点。
2. 查询从根节点开始，按目标键与节点内键值的大小关系选择分支。
3. 到达叶子节点后，拿到目标行在表中的位置，再读取完整行。

因此，索引把查找成本从随表大小线性增长，降低到随树高对数增长。树高通常很小，所以即使表很大，定位也只需要少量页面读取。

代价落在写入路径上：每个索引都要在插入、更新、删除时维护，索引越多，写入越慢、占用空间越大。覆盖索引可以减少回表，但会让索引更大。

## 例子 / 应用

```sql
SELECT * FROM orders WHERE user_id = 42;
```

如果 `user_id` 上没有索引，数据库需要扫描 `orders` 的每一行；有索引时，它可以先找到 `user_id = 42` 的索引项，再读取对应的行。

这个例子成立的前提是 `user_id` 的选择性较高。如果该列只有少量取值，索引可能仍然需要扫描大量行；查询条件对索引列使用函数或隐式类型转换时，数据库也可能无法使用索引，具体行为取决于数据库和版本。

````
