# 操作总结型笔记

## 适用场景

对话主要在讲“怎么做”：安装、配置、部署、迁移、排错、日常操作流程。读者希望照着做就能得到结果。

## 结构

按以下顺序组织；没有内容的小节直接省略。

1. `# <动作或结果>`：标题写用户能得到的最终结果，例如“在本机启动 PostgreSQL 容器”，不要写“数据库操作”。
2. 开头一句话：说明这篇笔记解决什么问题、适用于什么环境。可选。
3. `## 前置条件`：只在有硬性要求时写。列出操作系统、运行时、版本下限、权限、依赖、端口占用等。用短列表，不解释安装方法。
4. `## 操作概览`：可选。步骤较多时，用 3–6 条短句列出核心操作，每条对应后面的一个小节；步骤少时省略。
5. 核心步骤：每个逻辑操作一个 `##` 小节，标题用动词开头的短句，例如“安装依赖”“启动服务”“导入数据”。每节先给可直接复制运行的代码块；只在易错处补一句说明或一小段。
6. `## 验证`：给出验证命令和预期结果。
7. `## 清理 / 回滚`：可选。涉及创建资源、修改系统配置、不可逆操作时给出。

常见问题、易错点不单设章节；把现象 → 原因 → 处理写成对应步骤后的一句说明或一小段，只在会影响成败或后果严重的地方补充。

## 写作规则

- 精简优先。能一行命令说清，就不写一段话。
- 前置条件只写会影响成败的。不要写与成败无关的通用条件（例如“需要一台电脑”）。
- 代码块里放纯命令，不要放 `$` 提示符，不要混入输出。需要展示输出时，在代码块外用一句话说明，或单独放一个输出块。
- 命令按实际验证过的版本写。对话里用过 `sudo`、特定工作目录、环境变量的，保留。
- 占位符用 `<token>`、`<path>` 这种形式，并在首次出现处说明；散文中的占位符必须用行内代码包住，避免被 Discourse 当作 HTML 标签清理。不要用 `$TOKEN` 冒充占位符，除非它确实是环境变量；代码块内不受影响。
- 需要特定工作目录时，在代码块里 `cd`，或在前一句写明。
- 破坏性命令（删除、覆盖、重置、`rm -rf`、`DROP`）在代码块前用一句话警告。这是“说明放在 block 后”规则的例外。
- 验证步骤尽量给可执行的检查命令，而不是“检查是否成功”。
- 不解释命令原理。需要背景时，一句话带过或链接到另一篇笔记。
- 对话里的失败尝试只在能解释一个非显然的前置条件时保留，否则删掉。

## 示例

````markdown
# 在本机启动 PostgreSQL 容器

适用于本地开发和测试；生产环境请使用托管数据库或编排配置。

## 前置条件

- 已安装 Docker
- 本机 `5432` 端口未被占用
- 有权限拉取 Docker Hub 镜像

## 启动容器

```bash
docker run -d \
  --name notes-db \
  -e POSTGRES_PASSWORD=<password> \
  -p 5432:5432 \
  postgres:16
```

`<password>` 换成自己的密码；容器名 `notes-db` 在后续命令中会用到。

如果 `5432` 端口已被占用，`docker run` 会报 `Bind for 0.0.0.0:5432 failed`；停掉旧服务，或把 `-p` 改成 `5433:5432`。

容器启动后立即退出时，用 `docker logs notes-db` 查看原因，确认 `POSTGRES_PASSWORD` 已传入。

## 验证

```bash
docker exec notes-db pg_isready -U postgres
```

预期输出包含 `accepting connections`。

## 清理

```bash
docker rm -f notes-db
```
````
